Lección 02 · Spring Boot · Proyecto CRUD de productos

El patrón DTO

Qué es un DTO (Data Transfer Object) y qué problemas tiene exponer la entidad directamente, por qué hay uno para lo que entra y otro para lo que sale, qué es un record y cómo validar los datos con @Valid.

La idea en una frase Una clase para cada trabajo: la entidad para la tabla, un DTO para lo que entra y otro para lo que sale.
01 · El problema

La entidad hacía de todo

En la versión básica, el controlador recibía y devolvía directamente la entidad Producto. Funciona, pero la misma clase hacía tres trabajos a la vez: tabla, JSON de entrada y JSON de salida.

ProblemaEjemplo en este proyecto
El cliente puede mandar campos que no deberíaPodría enviar "id": 3 o "fechaCreacion": "2000-01-01" y colarlos en la base de datos.

02 · La solución

Una clase para cada trabajo

Un DTO es una clase cuyo único fin es transportar datos entre capas o hacia fuera. No tiene lógica ni está ligada a la base de datos.

  • ProductoResponse añade disponible, que no existe en la tabla.
  • La entidad solo se ocupa de la tabla, y ya no sale del servicio.
03 · Java

Los DTOs del proyecto son record

Un record (Java 16+) es una clase pensada para llevar datos. Con unas pocas líneas, Java genera solo el constructor, un método para leer cada campo, y equals(), hashCode() y toString().

Ojo al leer un campo El método se llama response.nombre(), no getNombre().
Inmutable Los campos son final y no hay setters: una vez creado, no cambia. Es una «foto» de los datos, justo lo que se quiere en un DTO.

¿Por qué la entidad Producto no es un record? Porque JPA necesita un constructor vacío y poder modificar los campos (por eso tiene setters). Entidad → clase normal; DTO → record. Spring y Jackson (la librería que convierte JSON ↔ Java) entienden los record sin configurar nada.

05 · Validación

Comprobar los datos al entrar

Como ProductoRequest representa justo lo que llega del cliente, es el sitio ideal para decir qué datos son válidos. Las anotaciones por sí solas no hacen nada: hay que pedir que se comprueben con @Valid en el controlador.

Si algún campo no cumple, Spring lanza MethodArgumentNotValidException antes de entrar en el método: el servicio ni se entera. El manejador de la lección 04 la convierte en un 400 con la lista de errores.

DTO o servicio El DTO comprueba que los datos tienen buena forma sin mirar nada más («el precio es positivo»). Las reglas que necesitan la base de datos («el nombre no está repetido», «hay stock») van en el servicio. Lo has visto en el validador con «teclado».
¿Y el nullable = false de la entidad? @Column(nullable = false) solo define cómo se crea la tabla. Antes, un null llegaba a PostgreSQL y la respuesta era un 500. Con la validación del DTO el error se detecta antes y es un 400 que dice qué campo está mal. La base de datos queda como última barrera.

La conversión entre unos y otros la hace el mapper, que es la siguiente lección.

Un DTO no tiene que parecerse a la entidad

El endpoint de ventas solo necesita un dato, así que su DTO solo tiene uno. Y RespuestaError (lección 04) es un DTO que no tiene nada que ver con ninguna tabla. Los DTOs se diseñan pensando en qué necesita el cliente, no en cómo es la base de datos.

Cómo comprobarlo

En peticiones.http, sección Lección 2. El test ProductoControllerTest.datosNoValidosDevuelven400SinLlegarAlServicio comprueba además que el servicio no se llega a llamar (verifyNoInteractions).

Errores típicos

Olvidar @Valid. Las anotaciones se ignoran sin dar ningún error, y se cuelan datos inválidos.
Llamar a request.getNombre() en un record. El método se llama request.nombre().
@NotNull en un String obligatorio. Dejaría pasar "" y " ". Para textos, @NotBlank.
@NotBlank en un número. Es solo para textos; en números, @NotNull.
Devolver la entidad «solo en este endpoint». En cuanto un endpoint la expone, vuelven todos los problemas.

08 · Para repasar

Si solo te quedas con 5 ideas

  1. Un DTO solo transporta datos. Uno para lo que entra (ProductoRequest) y otro para lo que sale (ProductoResponse).
  2. Lo que el cliente no debe decidir (id, fechaCreacion) no existe en el DTO de entrada.
  3. Los DTOs son record: inmutables, y se leen con nombre(). La entidad sigue siendo una clase normal.
  4. Las anotaciones del DTO solo se comprueban con @Valid; si fallan, 400 y el servicio ni se entera.
  5. El DTO valida la forma; el servicio, las reglas que necesitan la base de datos.
