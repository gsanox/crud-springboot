Tratamiento de excepciones

Cómo viaja una excepción desde donde nace hasta convertirse en una respuesta HTTP, cómo centralizar todos los errores con @RestControllerAdvice, qué código corresponde a cada error y por qué el cliente nunca debe ver detalles internos.

La idea en una frase El servicio lanza excepciones con significado y un único sitio decide qué respuesta HTTP le corresponde a cada una.
01 · El problema

Cada error, de su padre y de su madre

En la versión básica, ProductoNoEncontradoException llevaba @ResponseStatus(HttpStatus.NOT_FOUND). Funcionaba para ese caso, pero:

Trazas de Java

El JSON de error lo generaba Spring a su manera y, con DevTools, incluía la traza completa de Java.

500 que no lo eran

Un nombre vacío o un precio negativo acababa en un 500 (fallaba PostgreSQL), como si fuera culpa del servidor.

Formatos distintos

Un JSON mal escrito, un /api/productos/abc… cada uno salía con un formato diferente. Para quien programa el cliente, una pesadilla.

02 · La idea

El servicio lanza, un único sitio traduce

Un 404
ProductoServicethrow new ProductoNoEncontradoException(99)
ProductoControllerno la captura: la deja pasar
ManejadorGlobalExcepciones@ExceptionHandler → 404 + JSON
Cliente{"estado": 404, …}
  1. El servicio detecta el problema y lanza una excepción con significado. No sabe nada de HTTP.
  2. La excepción sube por la pila de llamadas: nadie la captura con try/catch, así que atraviesa el controlador.
  3. Antes de que llegue al servidor web, Spring busca un @ExceptionHandler que sepa tratarla.
  4. El handler decide el código HTTP y construye el JSON de error, siempre con el mismo formato.

Así ningún controlador tiene try/catch, y añadir un error nuevo es añadir un método en un solo sitio.

03 · El manejador global

@RestControllerAdvice y @ExceptionHandler

  • @RestControllerAdvice: «esta clase da consejos a todos los @RestController». Sus métodos se aplican a las excepciones que salgan de cualquier controlador.
  • @ExceptionHandler(X.class): este método trata las excepciones de tipo X y de sus clases hijas. Un mismo método puede atender varias.
  • Los parámetros los rellena Spring: la excepción y, si se pide, la petición (HttpServletRequest) para saber la ruta.
  • ResponseEntity<T> permite elegir a la vez el código de estado y el cuerpo: ResponseEntity.status(estado).body(cuerpo).

El formato común: RespuestaError

Todos los errores de la API tienen la misma forma. Es un DTO más (lección 02): un record pensado para lo que necesita el cliente. El mapa errores solo se rellena en los errores de validación; en los demás va vacío.

¿Cómo se elige el código? 4xx: el cliente ha pedido algo incorrecto y puede corregirlo (datos mal, recurso que no existe, conflicto con el estado actual). 5xx: ha fallado el servidor y el cliente no puede hacer nada. 06 · Detalles importantes

Gana el más específico

Una ProductoNoEncontradoException también es una RuntimeException y una Exception, así que podrían tratarla dos handlers. Spring elige el que tiene el tipo más cercano en la jerarquía. Exception.class solo recoge lo que nadie más ha tratado.

Exception→ manejarErrorInesperado (500, o el código de Spring)
RuntimeException(ningún handler propio: cae en Exception)
ProductoNoEncontradoException→ manejarNoEncontrado (404)
ProductoDuplicadoException→ manejarConflicto (409)
StockInsuficienteException→ manejarConflicto (409)

Al cliente, un mensaje genérico; al log, todo

Una traza o un mensaje de la base de datos puede revelar nombres de tablas, versiones de librerías o rutas del servidor: información útil para un atacante. Por eso el 500 dice solo «Ha ocurrido un error inesperado», y el programador lo ve todo en el log con log.error(..., ex). El if con ErrorResponse existe porque las excepciones propias de Spring (URL inexistente, verbo no permitido…) ya saben su código; sin él, la red de seguridad las convertiría todas en un 500.

Las nuestras son no comprobadas para que puedan subir libremente desde el servicio hasta el manejador global sin ensuciar cada método con throws.

¿Entonces nunca try/catch?

Sí, cuando puedes hacer algo útil con el error en ese punto: reintentar, usar un valor por defecto o traducir una excepción técnica a una de negocio. Lo que no hay que hacer es capturar una excepción solo para devolver un código HTTP desde el controlador.

Para saber más: ProblemDetail

Existe un estándar para el formato de los errores HTTP (RFC 9457, Problem Details), y Spring lo trae hecho con la clase ProblemDetail: campos como type, title, status, detail e instance.

Aquí se usa RespuestaError porque se entiende mejor al aprender, pero en proyectos profesionales verás ProblemDetail a menudo. La idea es la misma: un único formato para todos los errores.

Cómo comprobarlo

En peticiones.http, sección Lección 4, hay una petición para cada fila de la chuleta. ProductoControllerTest cubre todos los casos sin base de datos: @WebMvcTest carga el controlador y los @RestControllerAdvice, y al servicio simulado se le dice qué excepción lanzar con when(...).thenThrow(...). ./mvnw test -Dtest=ProductoControllerTest

Errores típicos

try/catch en cada método del controlador devolviendo un ResponseEntity de error. Es lo que el manejador global evita.
Capturar y no hacer nada (catch (Exception e) {}). El error desaparece y nadie sabe por qué los datos están mal.
Devolver 500 para errores del cliente (datos inválidos, recurso inexistente). El 500 es solo para fallos del servidor.
Devolver ex.getMessage() de un error inesperado. Puede contener SQL o detalles internos.
Olvidar @RestControllerAdvice, o poner la clase fuera del paquete com.saseformacion.crud: los @ExceptionHandler no se aplican.

08 · Para repasar

Si solo te quedas con 5 ideas

  1. El servicio lanza excepciones con significado; no sabe nada de HTTP.
  2. Un @RestControllerAdvice con métodos @ExceptionHandler traduce cada excepción a un código y un JSON, en un solo sitio.
  3. Todos los errores salen con el mismo formato (RespuestaError).
  4. 4xx si el cliente puede corregirlo; 5xx si ha fallado el servidor, con un mensaje genérico y el detalle en el log.
  5. Si varios handlers encajan, gana el más específico; Exception.class es la red de seguridad.
